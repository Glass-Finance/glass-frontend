# KYC (Identity Verification)

## Current behavior

Frontend-only integration against the Glass backend KYC API (`kyc-frontend-integration.md` is the contract source). Smile ID Biometric KYC is the provider; the frontend initiates a challenge with `{ idType, callbackUrl }` on `POST /kyc/attempts` — `callbackUrl` defaults to the Smile ID result webhook (`https://api.glasspay.app/api/v1/webhooks/smile-id`, the backend team's callback) and is start-attempt only. The browser never stores the token (memory only) and never sends ID numbers or selfies to Glass.

**Two separate Smile surfaces, two separate callback configs.** Glass talks to Smile server-to-server (`POST /v3/token`) and embeds _its own_ per-attempt callback (`…/webhooks/smile-id/attempts/{attemptId}`, from `app.smile-id.callback-base-url`). The browser SDK is configured independently: it requires its own `callback_url` on the init call (it does not read one out of the token) plus all five `partner_details` keys, which exist only on the browser side. `DEFAULT_SMILE_CALLBACK_URL` (`api/kyc.js`) feeds the SDK call and the start request; the backend currently ignores the request's copy (its `KycStartRequest` takes only `idType`) and both webhook paths are accepted, so the divergence is tracked, not resolved — see the comment on that constant.

**SDK config is validated before the call.** `utils/smileSdkConfig.js` builds the option bag from `VITE_SMILE_*` and throws one error naming every absent required option (`token`, `callback_url`, `product`, `partner_details.{name,logo_url,partner_id,policy_url,theme_color}`) rather than letting the SDK fail on the first one in a deploy. `VITE_SMILE_LOGO_URL` and `VITE_SMILE_PARTNER_ID` are read without defaults, so "unset" can't masquerade as "configured". `user_details` and `consent_information` are intentionally not sent: the SDK validates them only when present, Glass's token already carries the member's names and contact details, and asserting consent needs a consent surface that does not exist yet.

- **Wizard modal (primary surface):** `src/components/kyc/KycWizardModal.jsx` runs a 4-step flow (Overview/payoff → ID type → Capture prep → Status) with a pill stepper, the illustration system (`components/kyc/illustrations.jsx`: Phosphor duotone glyphs for stepper/rows, unDraw flat scenes for 40px+ surfaces — open license, no attribution; source SVGs in `src/assets/kyc/`, accent rewritten to `currentColor` and inlined via `vite-plugin-svgr`), a viewfinder-style capture-prep screen, and a live status narrative. The approved status card carries the celebration moment (pop-in scene + rings + confetti, `kyc-success-*` classes in `index.css`, killed under `prefers-reduced-motion`). It mounts `useKycFlow` (`components/kyc/useKycFlow.jsx`), which owns step state, smart initial step (derived from `GET /kyc` status), the Smile-ID error bounce-back, and bounded status polling. The capture-prep screen is Glass-built only — actual capture still happens inside Smile ID's hosted window.
- **ID types (picker vs labels):** the step-2 picker (`components/kyc/steps/IdTypeStep.jsx`) offers only what the backend's `KycIdType` enum accepts for a **new** attempt — `KYC_SUBMITTABLE_ID_TYPES` (`BVN`, `NIN_V2`), surfaced as `KYC_SUBMITTABLE_ID_TYPE_OPTIONS`. `ID_TYPE_OPTIONS` stays the complete 5-value label map and is derived-from, not replaced: history rows (`idTypeLabel`) and the platform-admin ID-type _filter_ (`KYC_ID_TYPE_FILTER_OPTIONS`) must still match attempts persisted under a retired value. Adding a card back to the picker without a backend enum value is a bug, not a feature.
- **Gates/badges open the wizard:** community create/manage (`useKycGate`) opens `KycWizardModal` directly (the old `KycRequiredSheet` interstitial is gone — no modal-on-modal), as do the KYC status badges on Communities Home, member Home, My Communities, and the Settings row. `historyPath` wires the footer's history link per shell. **Exception:** the onboarding create path no longer opens the modal — ChoosePath's Continue _navigates_ to the `/onboarding/verify-identity` step (see Gates below).
- **Onboarding verify step:** `/onboarding/verify-identity` is a thin `useKycFlow` shell (same structure as the dashboard page) sitting between ChoosePath and PayingMember. ChoosePath routes there only when the summary is known and not approved; approved/exempt (platform staff, kill switch)/failed-summary/settled-without-record all skip straight to PayingMember, and the step itself fails open the same way. Approved "Done" continues the create path; dismissal returns to ChoosePath; the SignUp email rides along in router state.
- **Reactive blocks:** catches the backend 403 (`isKycRequiredError` in `utils/kycStatus.js` — 403 + `"Approved KYC is required"`) where the client gate couldn't see it (stale summary, deep link, staff-role invite acceptance). Copy is shared: `KYC_ADMIN_BLOCK_COPY` (promotion dialog — dialog stays open with the reason inline, `ConfirmDialog`'s `error` prop) and `KYC_ACCEPT_BLOCK_COPY` (member accepting an invite that grants a staff role — inline notice above the invite list). `OrganizationProfile`'s submit-resume uses the same matcher.
- **Member:** `/member/verify-identity` reads `GET /kyc` as the source of truth, starts/refreshes an attempt, runs the Smile ID CDN SDK, then `confirm-submission` only on client success. Attempt history: `/member/verify-identity/history`. Both routes stay behind the member app's authentication guard and are available on desktop and mobile.
- **Dashboard (desktop):** `/dashboard/verify-identity` (+ `verify-identity/history`) is the dashboard-styled counterpart — a deep-linkable shell (direct URLs, the getting-started checklist, History) around the same flow. Interactive entry points (badges, gates, the Settings row) open the wizard modal inline instead of routing here.
- **One shared flow:** member page, dashboard page, and wizard modal are thin chrome around `useKycFlow`; the Smile ID state machine is `src/hooks/useKycVerification.js`. Pages render the stepper/steps/footer inline; the modal does it inside `GlassModal` (portal, focus trap, fixed footer). The footer holds one primary plus an optional secondary (`useKycFlow`'s `row`): paired, the primary absorbs the space the secondary leaves; **alone it centres under a 320px cap** rather than spanning the modal — that's a deliberate cap on `flex-1`, not an unfinished layout.
- **Status refresh:** on window focus and after mutations everywhere; while the flow is parked on a non-terminal status it additionally refetches every 6s, bounded at ~2 minutes (`MAX_POLLS` in `useKycFlow`), then settles into a "we'll notify you" card. The live narrative ("Uploading… → Checking document quality… → Verifying with issuer…") cycles only while status is in flight (`isKycInFlight`).
- **Status interpretation** lives in `src/utils/kycStatus.js` (labels, chips + pill dot colors, the per-state Phosphor icon map behind `kycStatusStyle().Icon`, `isKycApproved` / `isKycTerminal` / `isKycInFlight`, id-type labels, the reactive-block matcher + copy, and `kycCompletionState` which collapses the enum into the four badge states). Admin table colors also mirror the enum set in platform-admin `shared.js` `STATUS_COLORS`. Every status pill (`KycStatusBadge` — Home, Settings, Communities Home, My Communities) renders icon + label from that one map.
- **Gates:** community create/manage shows the wizard only when summary is explicitly not `APPROVED`. While the summary is still loading the trigger holds (disabled/spinner) — "still loading" never means "let them through". A failed summary fails open so a broken endpoint can't lock admins out; backend remains authoritative (`docs/authorization.md`). Platform staff are exempt per the backend contract (they can't start a personal attempt). On approval, the wizard's Done resumes the interrupted action — the gate remembers the continuation (create flow step, community card) instead of returning to the dashboard. The wizard re-submits a create the backend rejected with the KYC 403 (`"Approved KYC is required for community staff participation"` — stale client summary or a deep link past the gate); dismissing it drops the held submission and leaves the form intact.
- **Badges:** Settings Account row, Home header (when not approved), Communities Home header (every state, approved included — that screen is where the create-a-community decision is made), Create Community actions. Each opens `KycWizardModal` inline through a bare transparent `<button>` rather than the design-system `Button`, whose focus ring and box read wrong on a status pill. **Completion indicator (`KycStateBadge`, dashboard-only):** next to members' names in the Members table and beside role pills in Member Access — never on member-app surfaces. It renders nothing while the member DTO has no `kycStatus` field: the backend's `CommunityMemberResponse` doesn't carry one yet, so the wiring ships hidden and activates when that field lands (backend follow-up).
- **Platform admin evidence review:** Admin Panel → KYC lists `/admin/kyc/attempts` (default `IN_REVIEW`). Detail loads full evidence before the existing Approve/Reject flow; evidence approval still requires `IN_REVIEW` and `canApprove`. Attempt policy remains separate.
- **Platform admin manual approval/revocation:** Users rows show account KYC status and **Approve manually** / **Revoke KYC**. KYC attempt details expose the same user-level actions, using a fresh `/admin/users/{userId}` read rather than historical attempt status. These actions are shown for the documented `SUPER_ADMIN` / `OPERATIONS_ADMIN` grants; backend permissions remain authoritative. Manual approval uses `POST /admin/users/{userId}/kyc/approve` with a required trimmed `{ reason }`, bypassing verification stage and evidence requirements. The existing revoke endpoint supports profile-only approvals. Both confirmation flows reload target-user data before enabling submission; missing/unknown fields fail closed. The DTO does not expose every backend account eligibility condition, so the server still checks active/deleted/anonymized state.
- **Manual action state:** Confirmation identifies the target and explains that the action affects current account KYC. Duplicate submits and dismissal are blocked while pending. Success refreshes admin user, attempt, and audit caches; the result retains and displays the returned attempt ID and `Admin bypass: …` reason when present. Profile-only results legitimately have no attempt or summary reason; the reason remains in backend audit history. A `409` refreshes user/attempt data and requires an explicit **Review refreshed state** action before retry. Other failures retain the entered reason. Evidence and confirmation dialogs replace each other rather than stacking.
- **Contract/deployment:** [Admin Manual KYC Approval release note](https://app.notion.com/p/4009a22eb2a981a8843de695376ac723) and [KYC Frontend Guide](https://app.notion.com/p/3fe9a22eb2a981a898a7ceae5f200d7a). The deployed OpenAPI advertised `approveBypass` on 2026-10-22 and the strict endpoint audit passed. Authenticated live approval/revocation and notification delivery remain unverified; local browser verification uses a synthetic Postman simulation.
- **Kill switch:** `VITE_FLAGS={"kycDisabled":true}` hides member entry points and gates.
